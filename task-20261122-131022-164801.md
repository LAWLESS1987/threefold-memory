AFTER (outbound t263s1117, verbatim):
I worked on paper only. I haven't built anything or read the phone app's side.

1. **The meeting.** Comparing the full digests on both screens is sound against anyone on the network. "First pin wins" is not enough on its own, for three reasons.
   - Nothing confirms that the shared secret arrived intact. One device shows it and the other reads it, and nothing compares the result. Fix: after the transfer, both screens show a short code derived from the secret (for example the first 8 hex of HMAC(s3, "confirm")), and the owner compares them.
   - Nothing records the meeting as one fact. Each device should store a single hash over everything pinned (both RSA digests, both ML-KEM digests, the PSK name, the ML-DSA keys if any), and that hash should be shown on both screens and recorded on both.
   - Nothing says how the secret is displayed. A secret shown on screen can end up in a screenshot, the photo roll, the clipboard or a camera-app cache. The draft should say it is shown once, never saved anywhere but the pin store, and erased from the display.
   
   What's also missing is a way to lose trust without a meeting. If one device is lost or stolen, the owner can't meet it, so the remaining device needs a local "unpin this peer" step. It may only take trust away, never add it.

2. **The latches.** Nobody can unset them remotely. Locking the owner out needs only a lost secret, and that's the intended cost. The real hole is restoring from a backup.
   - A backup made before the meeting comes back with no pins and no latches, so that device seals and accepts version 1 again.
   - A backup made after the meeting brings back an old `seq`, so blocks sent after the backup can be replayed to it.
   - If the backup is in the cloud, it holds s3 as well, which gives a second provider the third secret.
   
   Fix: keep s3, the pins, the latches and the `seq` counters out of every backup, and have a restored, reinstalled or replaced device start latched with no peers. Then the only way back is another meeting.

3. **The block.** The derivation is sound, unchanged from draft 1. The exact-bytes rule for the header is right, and so is dropping `spk`. One problem is the byte form of the signed data and the envelope. "header bytes + { ek, kc, iv, ct }" and "over every field above" don't say what bytes are signed or how the envelope is serialised. The signature input should be a fixed, length-prefixed sequence (for example a label, then header bytes, `ek`, `kc`, `iv`, `ct`, each with a 4-byte length), and the envelope format should be spelled out the same way. `seq` is sound, but give it an upper bound (below 2^53, say) so JSON readers agree on it. Nothing draft 1 had is missing: the day, plan hash and nonce rules survive as rule 6.

4. **The reader's order.** Rule 5 is sound but not needed. A broken `ek` that still carries a valid signature can only come from the sender, because the signature covers `ek` and is checked first. So no outsider gets the RSA error oracle the rule guards against, and once RSA falls, s1 is lost anyway. Its only real cost is that the code has to catch the library's OAEP exception without a different log line or timing. Keep it only if that adds nothing to the error path. The order of the other rules is right.

5. **The table.**
   - Rows 1, 2, 3 and 5 are true for an outsider. Row 3's "cannot be forged" holds only for an outsider, since either device can make a valid block, which is fine for one owner. Row 5 should also name HKDF and HMAC.
   - Row 4 overclaims. A device that has been read gives up its RSA and ML-KEM private keys along with s3. Every block in the mail archive addressed to that device is then open, and the attacker can seal blocks as that device to the other one. Only blocks addressed to the unread device stay closed.
   - Two rows are missing. One is "s3 alone leaked, no device read" (through a backup or a photo of the screen), which is what row 4 seems to mean, and there the public-key schemes do hold. The other is "a device restored from backup", which is item 2 above.

6. **What I would cut.**
   - The 16-hex `to` and `from` in the header. They can be derived from the full digests for display, and two forms of one identity invite a lookup by the short one.
   - The RSA-signed pin statement in the ledger. It's never the authority, so a plain ledger entry carrying the meeting hash from item 1 says the same thing with no RSA dependency.
   - Rule 5's random s1, if catching the library's error adds any code path.
   - I wouldn't cut the ML-DSA key at the meeting: pinning it now saves another meeting later.

READY TO WRITE TEST VECTORS: no. The signature input and the envelope byte layout aren't fixed yet.
Most important change: keep s3, the pins, the latches and the `seq` counters out of every backup, and have any restored, reinstalled or replaced device start latched with no peers, so the only way back in is another meeting.
